# 交易复盘与历史结单导入

2026-09-05 最新界面已按用户要求调整为成交详情、简短逐笔复盘和宏观周报；交易计划入口已移除，原计划数据和兼容接口继续留存。

在现有网页的「交易复盘」页使用。复用登录权限、手工账本、券商成交与宏观判断；新增数据独立持久化于同一个 SQLite 数据库。

2026-09-11：新增券商定时读取与自动配对，同步后自动更新总览和券商累计净盈亏。Tradier结算净现金用于配对净收益；原始结单/档案保持。当前规则和验收以 [Handoff](HANDOFF.md) 的9月11日记录为准。

## 已实现的流程

- **交易档案**：将成交归为一笔策略，组合逐腿保留，一笔成交只能归属一个档案。也可以先建空档案，交易前记录计划。
- **成交详情**：按组合各腿展示开仓与平仓的数量加权均价、数量、费用、剩余数量与已完成腿净盈亏。逐笔明细保留成交价、金额、费用分项、净现金和结单页码。开平标记来自报表，或完整且无时序歧义的成交；信息不足时不推断。
- **交易计划**：界面已移除；现有记录保存在数据库，可在档案导出中查阅，不删除历史。
- **证据与操作**：手动事实和解释，关联新闻及已有宏观判断，保存当时内容快照。信息可获得时间、实际发生时间、记录时间分别保存，未知时间保持为空。
- **逐笔复盘**：仅要求「复盘结论」与「下次改进」。路径、心理、执行评价和证据折叠为可选项。未完成交易显示暂定，完成交易显示事后复盘；每次结论追加留存。
- **周末复盘**：按日期和券商绘制档案净盈亏折线，支持每日与周内累计、币种和券商筛选；独立的原始券商成交视图展示日期分布、成交内容和券商提供的已实现盈亏，两种来源不相加。宏观周报记录当周变化、市场影响、下周机会与带时间/时区/来源的关键事件。图表输入随周报冻结保存。旧周报的成长记录仍可查看。
- **图文学习**：逐字保留压缩包的 `01-图文内容手册.md`，按章节阅读、全文检索并可下载；十张原图保持比例。资料包自己含有标明的编辑摘要，未获得包外原始对话，不虚称恢复原始聊天逐字稿。
- **个人规则**：经验示例完整保留在资料包正文；原计划中的规则快照保留，当前界面不再编辑交易计划。
- **50/25/25 教学算例**：固定初始借方成本，分开显示回收现金、已实现利润与尾仓成本，整数合约出现小数时提示。该算例不依据行情触发，不生成成交，也不维护自动执行阶段。
- **导出资料**：导出本档案、相关知识卡与资料包的复盘助手提示词。自动移除券商成交外部标识与账户关联键；用户自由文本仍应自行检查。当前没有调用外部 AI，`OPENROUTER_API_KEY` 为空。

## 自动匹配的证据来源：Tradier 已平仓批次与当日订单（2026-09-20）

自动配对第 1 步为成交补充券商自己的证据，不改变任何已记录的价格、数量、费用、净现金和报表日期，也不增删成交。

- **已平仓批次（`GET /accounts/{id}/gainloss`）**：每夜可得，含标的、批次数量（正为多头批次、负为空头批次）、开仓/平仓日期、成本与收入。同步时按“同标的 + 同日期 + 同买卖方向 + 净现金相等”把批次的开仓腿与平仓腿匹配到成交，写入 `positionEffect`（open/close）、`lotId`（同一批次的开平成交共用）与 `effectSource: "lot"`；金额不一致时只在同日同向剩余成交唯一时按数量匹配；再无法唯一匹配的成交，只要该标的当日涉及的批次方向一致，也按“多头批次买入=开仓、卖出=平仓（空头相反）”补开平标记但不给批次 id。仍未平仓的成交没有批次，保持空。真实回放：27 笔 Tradier 成交中 24 笔获得开平标记与批次配对，3 笔为仍持有的 UCO 两腿与 DRAM Put；基础字段与生产逐字段一致（`data/tradier-orders-20260920/dry-run.json`）。
- **当日订单（`GET /accounts/{id}/orders?includeTags=true`）**：Tradier 只返回当前交易日的订单，历史订单不可查（2026-09-20 实测返回空）。因此每次 15 分钟同步都会把 `filled`/`partially_filled` 订单按腿保存到 `broker_order_observations`（键：券商/环境/账户/订单或腿 id，保留首次与最近观察时间）；多腿单以父订单 id 作为 `groupId`。下一夜成交历史到达后，按“同标的 + 同日期 + 同方向 + 数量相等（部分成交按合计）”匹配，写入 `orderId`、`orderGroupId`、`executedAt`（秒级）以及来自 `buy_to_open` 等字段的开平标记（`effectSource: "order"`，优先于批次标记）。订单证据只能从上线后的交易日开始积累；服务停机期间下的单不会被补造。
- **复盘层的使用**：`availableReviewFills` 对有 `executedAt` 的 Tradier 成交以该时刻作为 `occurredAt`（精度 instant），否则仍用报表日期；`positionEffect` 直接进入自动配对与开平分类；已建档案读取时（`currentTradingCases`）同样补充批次/订单证据和更精确时间，存储的原始成交不改写。`ReviewFill` 新增 `lotId`、`orderGroupId` 供后续策略簇使用。
- **手动合并实例（2026-09-20）**：UCO 10/16 两腿合并后按同日档识别为看多认购价差；SPY 9/14 四个行权价合并为一个档案（10 笔成交，整笔净盈亏 −30.20 USD，已退出），但四腿为 757 空头 1 张、758/761 多头各 1 张、762 多头 2 张，数量不等且不属 20 种标准结构，保持“多腿组合 · 方向分别见各腿”并逐腿显示开平均价与腿盈亏。
- **未覆盖**：IBKR Flex 尚未加入 `ibOrderID`；沙盒账户没有成交历史；批次匹配不能区分同日同标的、同向且金额相同的多笔成交之间的先后（它们的标记相同，批次 id 按出现次序分配）。

## 收盘前 1 分钟的 Tradier 同步（2026-09-20）

Tradier 只返回当前交易时段的订单，因此除每 15 分钟的常规同步外，`apps/server/src/session-close-sync.ts` 在每个交易日常规收盘前 1 分钟（按 Tradier 交易日历的 `open.end`，含提前收盘；日历未读取时按工作日 16:00 ET，休市日跳过）再读取一次 Tradier，捕获当日多腿订单的腿分组、开平标记与秒级成交时间。判定窗口 90 秒、每个日期只执行一次，与常规同步共用同一同步锁，仍是只读；盈亏日 K 的北京时间 12:00/00:00 记录不变。`GET /api/brokers` 的 Tradier 连接返回 `closeSync`（下次执行时刻、依据、最近执行日期），券商页显示该行。收盘后到次日凌晨的订单仍由 15 分钟同步覆盖；服务停机期间的订单不会补造。

## 结构识别的两档口径与 Tradier 时间精度（2026-09-20）

- **精确档（默认）**：多腿结构识别要求各腿开仓为同一已核实时刻（`openingAt` 相同的 instant 成交），来自当日订单观察、大象结单等秒级来源；`IdentifiedStrategy.timing = "exact"`。
- **同日档（仅用户确认的分组）**：手工新建的档案，或用户手动合并过的自动档案（`linkHistory.mergedFrom` 存在且 `pairingBasis` 不以“自动合并”开头），当各腿同标的、同到期、同乘数、同币种、开仓在同一报表日且每笔开仓有明确开仓标记时，也识别结构，标签追加“· 按同日开仓识别（用户已确认）”，`timing = "same-day"`。自动合并或未经用户动作的自动档案不适用，仍显示逐腿说明。判定入口 `userConfirmedGrouping`，实现见 `identifyStrategy(legs, { sameDayConfirmed })` 与 `reviewExecutionDetails`。
- **Tradier 能否给出精确开仓时间**（2026-09-20 查阅官方文档）：
  - 成交历史 `GET /accounts/{id}/history`：文档明确“不包含仓位或订单创建/关闭的具体时间（时/分）”，也“不包含订单号”。
  - 订单 `GET /accounts/{id}/orders`：只返回“当前交易时段”的订单，含 `create_date`/`transaction_date`（秒级）与多腿 `leg[]`；历史不可查。单个订单 `GET /accounts/{id}/orders/{id}` 文档未说明时间范围，且需要已知订单 id。
  - 已平仓批次 `gainloss`：schema 为 date-time，文档示例带时刻，但本账户实测 12 条全部为 `T00:00:00.000Z`，只能当日期使用。
  - 账户事件流（Beta）：`wss://ws.tradier.com/v1/accounts/events`，先创建账户流会话（短时有效，需立即连接并实现重连），推送 `order` 事件（`id`、`status`、`avg_fill_price`、`exec_quantity`、`transaction_date`、`create_date`、`account`），文档未说明多腿逐腿明细，也未提供断线补发。它能把成交时间精确到毫秒，但需要常驻连接；断线期间事件丢失只能靠当日订单轮询补齐。
  - 结论：历史成交无法追溯精确时间；精确时间只能在成交当日通过订单轮询（已上线，每 15 分钟）或事件流（可选，常驻连接）捕获。

## 自动匹配第 2 步：策略簇与多腿自动合并（2026-09-20）

在按合约切出的开平仓周期之上，`packages/domain/src/strategy-clusters.ts` 把周期归为策略簇，证据强弱决定处理方式：

| 证据 | 判定 | 处理 |
| --- | --- | --- |
| `order` | 任意成交共享同一个多腿订单 id（`orderGroupId`），含一腿平、一腿开的滚仓单 | 自动合并为一笔策略，不要求结构可识别 |
| `instant` | 同账户、同币种、同标的（期权按标的解析）、各腿开仓为同一秒的 instant 成交，且各腿平仓也同秒或均未平 | 只有 `identifyStrategy` 识别出结构（垂直价差、跨式/宽跨式、蝶式、鹰式等）才自动合并，否则只给建议 |
| `day` | 同账户、同标的、同报表日开仓且同日退出或均未平，缺少秒级时间与订单号 | 永不自动合并，只列为“建议合并”，需人工确认 |

- 簇的证据取最弱一条边（有任何日期级连接就整簇按 `day` 处理）；不同账户/环境、不同币种、同一合约的多个周期从不归为一簇。日期精度的成交不猜顺序，也不因此分组。
- `syncAutomaticTradingCases` 对可自动合并的簇：全部成交未归档案时建一个多腿档案（标题为“来源 · 标的 · 结构或 N 腿组合 · 日期”，`pairingBasis` 写明依据）；涉及的已有档案全部是无复盘/证据/操作/计划记录的自动档案且成交都在簇内时，自动合并到最早建立的档案（`linkHistory.mergedFrom` 记录来源，`pairingBasis` 以“自动合并：”开头）；否则退回逐周期逻辑并留作建议。用户已修改过资料或有记录的档案不会被自动动。
- `GET /api/trading-review` 新增 `suggestions`：对已经拆开的档案，簇内若至多一个有复盘记录，以它（否则以最早建立者）为目标，其余无记录且完全在簇内的档案为来源。页面在档案列表顶部列出建议，目标档案详情提供“按建议合并”（走现有 merge 接口，需确认），来源档案提示所属目标；“合并其他档案”面板预勾选建议来源。
- 现有数据：Tradier 历史成交是日期精度且今天尚无订单观察，因此上线后不会自动合并任何既有档案；SPY 9/14 的四个档案与 UCO 两腿只会出现为 `day` 级建议。订单证据从上线后的交易日累积，之后同一多腿单会在成交历史到达时直接生成一个多腿档案。
- 测试：`tests/workspace/strategy-clusters.test.ts` 覆盖订单簇（含未识别结构与跨账户）、同秒可识别价差自动合并、对角价差仅建议、腿退出时间错开不归簇、日期级仅建议、建议的目标选择、两种驱动下先拆后合并的幂等同步，以及已复盘档案只作建议。

## 档案资料、合并与当时的日报（2026-09-20）

- **档案资料可编辑**：详情页“编辑档案资料”可修改标题、策略意图、持有周期、工具类型（`POST /api/trading-review/cases/:id/profile`，字段同新建校验）。每次修改把旧值追加到 `profileHistory`，成交、证据、操作和复盘记录不受影响。自动配对档案会提示补充真实策略意图与周期。
- **合并档案**：“成交明细 → 合并其他档案到本档案”列出所有没有复盘、证据、操作和计划记录的档案（同标的排前），勾选后 `POST /api/trading-review/cases/:id/merge`（`{sourceCaseIds}`，最多 20 个）在同一事务内把来源成交归属改到本档案、删除来源档案，并在本档案 `linkHistory` 追加 `mergedFrom`（来源 id、标题、成交）。用于把自动配对拆开的价差各腿或分批成交并回同一策略，这样 20 种开仓结构识别才能覆盖自动档案。已有记录的档案拒绝合并（409），合并不可撤销；`historyComplete` 取各方的与。自动配对不会重新生成已合并的来源；被合并腿的后续新成交因目标档案含其他腿而不再自动追加，需在“补充成交”中手动关联。
- **当时的市场日报**：详情在成交摘要下方读取开仓前 3 日至退出日（未退出则开仓后 5 日，不超过今天）之间已保存的日报，显示日期、市场判断与摘要/正文摘录，点击跳转 `#/research/daily/<id>`。开仓结构与日报方向是否一致由人工判断，不自动评分。
- **列表与直达**：档案可按最近开仓/最近退出/等待复盘优先/净盈亏排序；筛选新增“等待复盘（已退出未复盘）”，顶部“等待复盘”统计可点击应用该筛选；OCC 期权符号在列表和详情显示为“标的 · 到期日 · Call/Put 行权价”可读标签（存储标题不变）。子栏目与所选档案写入地址 `#/trading-review/<tab>[/<caseId>]`，刷新或分享链接可回到同一档案；周报表单未保存内容镜像到本机浏览器，保存后清除。

## 期权方向与组合识别

2026-09-11 已上线：持仓和复盘优先显示标的方向。买入 Put 为看空、买入 Call 为看多；卖出开仓方向相反。“合约多头/空头”描述买入/卖出持有，买入平仓是空头回补。不会因方向显示更改买卖记录、结算现金或盈亏符号。参考 [OptionStrat 策略分类](https://optionstrat.com/strategies)。

自动识别20种常见开仓结构：4种单腿、4种垂直价差、买卖跨式/宽跨式、买卖认沽/认购蝶式，以及铁鹰/铁蝶及其反向。复盘列表和详情显示开仓结构；已识别期权提供对应公开说明链接。组合要求同标的、到期日、已知乘数及适当数量比例，且已有档案中各腿有精确同时开仓依据；不同开仓批次、日历或比例等未覆盖组合不强行分类。组合标签描述开仓时的结构，不是部分平仓后的实时敞口。

只有日期且缺少开平标记的相反成交仍可按真实现金核算完整配对净盈亏，但方向保持待核实，不按返回列表顺序决定多空。

## 金额与时序

整笔策略逐腿数量全部归零、确认成交完整且价格、费用、乘数及币种可核实时，计算净盈亏。部分退出不计为胜负。胜率分母含盈利、亏损与持平；没有亏损样本时，平均盈亏比为空。不同币种不加总。

R 只采用首次入场前记录的第一份固定风险计划，需正数金额、相同币种与可验证的精确入场时间。事后补记不产生 R。现有 IBKR 报表时区未知时，不将其日期自行转换成 UTC。

周报分别展示本期已完成整笔策略表现与本期成交净现金，不把现金等同于已实现盈亏。跨周及部分退出的期间已实现盈亏未在此另行分摊。缺少连续估值序列时，不展示推测的账户最大回撤、最大浮盈浮亏或回吐率。历史结单的未退出数量只代表所提供记录，不冒充最新券商持仓。

原计划正文、证据快照、成交快照及周报保持留存；手工账本的后续编辑或删除不会修改旧复盘证据。计划时序标签会根据新关联的成交重新判断，原记录时间保持不变。

## 结单导入

原文件位于 `trade_file/`，已排除 Git 和 Docker 构建。提取文本、解析结果、演练数据库和导入核对记录保存在被忽略的 `data/` 下；不放入公开静态资源。

识别脚本仅支持此次核验过的大象和 Tradier PDF 布局，依赖宿主已有的 PyMuPDF。布局变化、费用不平、数量或金额异常时停止。不会把期初期末持仓、银行划拨和汇总行误认为成交。

```bash
python3 scripts/parse-trade-statements.py trade_file data/import/parsed.json
node scripts/import-trade-statements.mjs --input data/import/parsed.json
# 对现有库预检新增文件、档案及待补充的原档案：
node scripts/import-trade-statements.mjs --input data/import/parsed.json --database /path/to/invest.sqlite
# 自动进行 SQLite 在线备份，成功后才在单个事务内写入：
node scripts/import-trade-statements.mjs --input data/import/parsed.json --database /path/to/invest.sqlite --apply --backup /path/to/new-backup.sqlite
```

脚本核对每笔 `数量 × 价格 × 乘数 = 成交金额`，逐项费用、小计、买卖净现金及文件汇总。标识基于账户归属散列、证券、方向、原始时间和成交字段；Tradier 另使用 Tag Number 区分同日成交。重复导入相同批次不会新增数据。不同来源之间不能仅凭金额相同就假定为同一账户成交。

2026-09-23 起支持增量续接：解析时包含目录中的历史结单，新增平仓按原成交归属补入已有单腿或双腿档案，保留档案 id、资料、原始成交及全部复盘记录，只追加成交和 `linkHistory`；新策略另建档案。若跨多个已有档案、新增合约会改变已有用户分组、旧文件内容有冲突，整批拒绝，不自动覆盖或合并。CLI 要求数据库已存在，默认只预检，`--apply` 写前进行 SQLite 在线备份；备份路径须可写且不能已存在。写入事务内重新校验归属，冲突整批回滚；不进行服务迁移或重建。

大库备份固定 WAL 读取快照，以 8192 页分批复制；不持有写锁，避免持续行情写入使默认小批次备份反复重启。生产备份目录的容器属主为 UID 10001；宿主 `docker cp` 的 0600 文件进入容器后需核对属主，不通过放宽敏感文件权限解决。成交导入后仍使用 `parse-elephant-positions.py` 和 `import-elephant-positions.mjs` 更新最新期末快照，再重载配置使新增持仓进入原报价调度；不补写过去的盈亏日 K。

无成交的大象结单也可留存（0 笔成交、成交金额/成交费用/成交净现金均为 0）：必须有结单日期、期初/期末资产摘要及已交收资金摘要，且无成交表或成交汇总。出现成交表却解析不出行仍会停止。银行划拨、入出金、融券费用及持仓估值不作为成交；零成交费用不代表该日没有其他账户费用。

大象结单说明时间为香港时间，导入时转换为 UTC。Tradier 确认书仅提供交易日，保留日期精度。合约乘数从明确的成交金额等式核对得出，费用按实际字段计入。每笔保留文件名、SHA-256、页码、行序、原始时间和费用分项。

同券商、同到期标的、同一时刻、等量反向期权开仓可归为双腿档案；缺少时刻的成交不会据此推定组合。归组依据作为导入证据保存，不生成用户的交易动机或事前计划。
